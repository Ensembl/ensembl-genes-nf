# IsoQuant integration specification

## 1. Purpose

Add IsoQuant as an independent long-read transcript-discovery workflow in the
`long_read_tama` pipeline. The primary use case is **annotation-free initial
annotation**: start with a reference genome and aligned long reads, but do not
provide an existing gene annotation to IsoQuant.

Reference-guided IsoQuant is a useful secondary mode for read assignment,
quantification, splice-site correction, and comparison against an existing
Ensembl annotation. It must not become an implicit prerequisite for the
annotation-free workflow.

IsoQuant is not another TAMA/StringTie-style collapse followed by a generic
merge. It constructs transcript models from spliced long-read alignments and
can also emit read-to-model assignments and abundance tables. The integration
must therefore preserve its native output and run it as an isolated branch
from the original sorted BAMs.

## 2. Scientific rationale

The IsoQuant paper describes an intron-graph method for reconstructing
transcripts with and without a reference annotation. Its reported advantage is
especially relevant here: novel transcript discovery is intended to retain
useful recall while reducing false-positive models. The paper also evaluates
both PacBio and Oxford Nanopore data and uses the same aligned BAM and
reference annotation across tools for comparisons.

For the Ensembl long-read use case, the most important output is not merely a
GTF model count. The workflow should retain:

- discovered transcript structures;
- the reads contributing to each discovered transcript;
- per-read assignment classifications;
- transcript/gene counts and TPMs where applicable;
- splice-junction and end-support evidence where produced; and
- tool/version/parameter provenance.

These outputs make IsoQuant useful both as a candidate model generator and as
a source of evidence for filtering models generated by TAMA, StringTie2,
StringTie3, or tmerge.

## 3. Scope and non-goals

### In scope

- IsoQuant annotation-free transcript discovery from sorted, indexed BAMs.
- Optional reference-guided IsoQuant using a supplied GTF/GFF annotation.
- PacBio CCS and Oxford Nanopore data-type selection.
- Per-accession and cohort-level execution options.
- Preservation and publication of IsoQuant's native GTF, read-information,
  read-to-transcript, count, and provenance files.
- Conversion of IsoQuant transcript models to BED12 for common structural QC.
- Comparison with the existing native backend outputs.

### Out of scope

- Passing IsoQuant output through TAMA, tmerge, or StringTie merge.
- Treating IsoQuant's annotation-free output as automatically release-ready
  Ensembl annotation.
- Replacing the existing minimap2 alignment policy as part of this change.
- Adding short-read correction, single-cell/barcode handling, fusion detection,
  or SQANTI products in the first implementation.
- Selecting biological thresholds before the first controlled benchmark.

## 4. Workflow topology

The current pipeline produces one sorted and indexed BAM per approved run.
IsoQuant should branch from that channel **before** contig sharding:

```text
approved long-read input
    -> minimap2 splice alignment
    -> samtools sort and index
    -> per-accession sorted BAM + BAI
          |\
          | \-> existing contig-sharded TAMA/StringTie/tmerge workflows
          |
          \-> IsoQuant on the complete accession BAM
                -> native IsoQuant output directory
                -> transcript_models.gtf
                -> read_info/read-to-transcript evidence
                -> counts and QC
                -> derived BED12 for comparison only
```

IsoQuant should not be run independently on every contig shard and then
merged as though it were StringTie. Its model construction is gene/locus
oriented and its read-assignment outputs are meaningful only when the input
scope and output provenance are explicit.

### Recommended execution scopes

The implementation should support these scopes:

| Scope | Purpose | Recommendation |
|---|---|---|
| `accession` | One IsoQuant result per input run | Required for per-sample diagnostics |
| `cohort` | One IsoQuant run over all approved accession BAMs | Recommended primary initial annotation |
| `both` | Produce independent accession and cohort results | Recommended benchmark mode if resources permit |

The cohort run must be a fresh IsoQuant run over the complete set of sorted
BAMs. It must not concatenate or re-merge per-accession IsoQuant GTFs using a
different tool. IsoQuant supports multiple BAM inputs and produces one
combined annotation, with per-file expression columns where applicable.

Accession results remain valuable for identifying batch- or sample-specific
models, but the cohort result is the principal candidate set for initial
annotation.

## 5. Modes

### 5.1 Annotation-free mode: primary

Inputs:

- reference genome FASTA;
- sorted/indexed BAM(s) from the pipeline's minimap2 alignment;
- no `--genedb` argument.

Required IsoQuant analysis:

```text
transcript_discovery
```

Expected primary model output:

```text
<sample>.transcript_models.gtf
<sample>.transcript_model_reads.tsv.gz
<sample>.read_info.tsv.gz
<sample>.discovered_transcript_counts.tsv
<sample>.discovered_transcript_tpm.tsv
```

The exact filenames must be checked against the pinned IsoQuant version and
captured in a manifest rather than assumed by downstream processes.

Annotation-free mode must not silently import an Ensembl GTF for splice-junction
guidance, transcript assignment, or model filtering. The only biological
reference supplied to this mode is the genome FASTA, plus the alignment and
data-type parameters.

### 5.2 Reference-guided mode: secondary

Inputs:

- reference genome FASTA;
- sorted/indexed BAM(s);
- `--genedb` GTF/GFF or prebuilt gffutils database;
- `--complete_genedb` when the annotation is an official annotation with
  `gene` and `transcript` features.

Recommended analyses:

```text
transcript_discovery quantification
```

This mode is intended for:

- known-transcript assignment;
- transcript quantification;
- read-level evidence for existing annotation;
- splice-site correction and comparison;
- separating known and novel models.

It is not the default because the initial-annotation use case often has no
trusted gene annotation available.

## 6. Proposed parameters

The parameters below are proposed names. They should be added to
`nextflow.config` and `nextflow_schema.json` only when the corresponding
implementation exists.

### Backend selection

```text
model_backend = tama|stringtie2|stringtie3|tmerge|isoquant|flair|all
```

`isoquant` enables only IsoQuant. `flair` enables only FLAIR. `all` enables all
six independent model builders. Existing `backend_merge_mode` applies only to
TAMA, StringTie2, StringTie3, and tmerge; it must not route IsoQuant or FLAIR
through a common merge.

### IsoQuant mode and scope

```text
isoquant_mode = annotation_free|reference_guided
isoquant_scope = accession|cohort|both
```

Defaults:

```text
isoquant_mode = annotation_free
isoquant_scope = cohort
```

The default deliberately reflects the initial-annotation use case. `both` is
the recommended explicit setting for a benchmarking run.

### Inputs

```text
isoquant_data_type = pacbio_ccs|nanopore|assembly
isoquant_genedb = null
isoquant_complete_genedb = false
```

Rules:

- `reference_fasta` is always required for IsoQuant, including when BAM input
  is supplied.
- `isoquant_genedb` must be null in `annotation_free` mode.
- `isoquant_genedb` is required in `reference_guided` mode.
- `isoquant_complete_genedb` should normally be true for official Ensembl,
  GENCODE, or RefSeq-style annotations.
- `isoquant_data_type` must be explicit or derived from an approved manifest;
  it must never be guessed from a filename.
- `pacbio_ccs` is appropriate for PacBio HiFi/CCS reads; `nanopore` is
  appropriate for ONT reads. `assembly` is not a substitute for either read
  type and should be enabled only for an actual transcript-assembly input.

### Analyses and evidence outputs

```text
isoquant_analysis = transcript_discovery
isoquant_large_output = read_info read2transcripts
isoquant_read_group = none
isoquant_report_novel_unspliced = false
isoquant_check_canonical = false
```

For annotation-free discovery, `transcript_discovery` is mandatory. The
reference-guided default should be:

```text
isoquant_analysis = transcript_discovery quantification
```

`read_info` and `read2transcripts` should remain enabled by default because
read-level support is central to the filtering objective. `read_assignments`
may be added as a compatibility output if downstream Ensembl tooling requires
that older format.

`isoquant_report_novel_unspliced` must be exposed rather than hidden. IsoQuant
does not report novel mono-exonic ONT transcripts by default; enabling this
option can be important for some annotation projects but may increase the
false-positive burden. It should be benchmarked explicitly rather than changed
silently.

### Runtime and storage

```text
isoquant_container = <pinned production container>
isoquant_args = ''
isoquant_threads = null
isoquant_high_memory = false
isoquant_genedb_output = null
isoquant_publish_native_intermediates = false
```

`isoquant_args` is an escape hatch for tool options not yet promoted to the
schema. It must be recorded verbatim in the run manifest. It must not be used
to override the mode, reference annotation, input BAMs, or output directory.

`isoquant_genedb_output` is relevant to reference-guided runs on shared
storage, where the tool's annotation database should be created in a suitable
local/scratch location. It is not needed in annotation-free mode.

The production container must pin IsoQuant and its Python dependencies. The
container must expose `isoquant` and the required `samtools`/BAM libraries and
must pass a toy `isoquant --test` check before a real run is accepted.

## 7. Proposed process and module boundaries

### `modules/isoquant.nf`

One primary responsibility: run IsoQuant on one execution scope.

Input contract:

```text
tuple val(meta), path(bams), path(bais), path(reference_fasta),
      path(optional_genedb), val(scope), val(data_type)
```

The actual tuple should avoid optional `path` values where Nextflow channel
semantics make them ambiguous. Prefer separate mode-specific process calls or
an explicit empty/sentinel file contract.

Output contract should include:

```text
tuple val(meta), val(scope), path(native_output_dir), emit: native
tuple val(meta), val(scope), path(transcript_models_gtf), emit: gtf
tuple val(meta), val(scope), path(transcript_model_reads), emit: model_reads
tuple val(meta), val(scope), path(read_info), emit: read_info
path 'isoquant_manifest.tsv', emit: manifest
path 'isoquant_versions.yml', emit: versions
```

Because IsoQuant creates several files with version-dependent names, the
process should stage the complete output directory and use a small helper to
discover, validate, and rename/copy the required products into stable names.
The helper must fail if the expected transcript model or read-evidence files
are absent.

### `subworkflows/run_isoquant.nf`

Responsibilities:

- select the complete sorted BAM channel before contig sharding;
- construct accession/cohort input groups deterministically;
- enforce annotation-free versus reference-guided input rules;
- invoke IsoQuant with the correct data type;
- collect native outputs and provenance;
- emit canonical transcript models for common validation.

### `modules/isoquant_to_bed12.nf`

Convert only the final IsoQuant transcript-model GTF to BED12. This output is
for structural comparison and existing validation products. It must not feed
any TAMA, StringTie, or tmerge merge process.

The converter must preserve a mapping from BED12 model ID to IsoQuant
transcript ID and retain the original GTF as the source of truth.

### `modules/audit_isoquant_outputs.nf`

Produce a stable manifest containing at least:

```text
backend
scope
accession_or_cohort
isoquant_version
data_type
mode
reference_fasta_sha256
genedb_sha256_or_NONE
input_bam_names
input_bam_checksums
transcript_model_count
read_info_count
read_to_model_record_count
output_file
output_sha256
complete
```

The audit must distinguish an empty result from a failed process and must not
call a partial result complete.

## 8. Deterministic command shape

The command should have the following conceptual form for annotation-free
cohort discovery:

```bash
isoquant \
  --reference reference.fa \
  --bam accession_1.sorted.bam accession_2.sorted.bam ... \
  --data_type pacbio_ccs \
  --analysis transcript_discovery \
  --read_group none \
  --large_output read_info read2transcripts \
  --output isoquant_output
```

The exact executable name (`isoquant` or `isoquant.py`) and output filenames
must be pinned to the selected container version. The command must not include
`--genedb` in annotation-free mode.

For reference-guided mode, add:

```bash
  --genedb annotation.gtf \
  --complete_genedb \
  --analysis transcript_discovery quantification
```

The pipeline should construct a sorted input file list and checksum it, as it
already does for the native backend merge inputs. BAM ordering and scope are
part of the benchmark and must be reproducible.

## 9. Relationship to existing backends

IsoQuant must be represented as an independent backend in finalisation and
comparison products:

```text
tama_combined_models.bed
stringtie2_combined_models.bed
stringtie3_combined_models.bed
tmerge_combined_models.bed
isoquant_combined_models.bed
```

The common canonical BED12 representation is only a comparison layer. The
native source products remain:

| Backend | Native source of truth |
|---|---|
| TAMA | TAMA BED12 and reports |
| StringTie2 | StringTie2 GTF and attributes |
| StringTie3 | StringTie3 GTF and attributes |
| tmerge | tmerge GTF/reports |
| IsoQuant | IsoQuant transcript-model GTF, read information, and counts |

The final QC should compare:

- exact or tolerance-adjusted intron chains;
- transcript-end agreement;
- locus-level overlap;
- read support per model;
- junction support and canonicality;
- model abundance/read counts;
- ORF/protein evidence where applicable; and
- agreement with trusted annotation only in reference-guided or external-QC
  analyses.

Raw model count must not be used as the primary ranking criterion.

## 10. Initial-annotation benchmark design

The first IsoQuant benchmark should use the same approved cohort and the same
minimap2 sorted BAMs as the existing backend comparison.

Minimum matrix:

| Run | Annotation | Scope | Data type |
|---|---|---|---|
| A | none | cohort | correct platform type |
| B | none | accession | correct platform type |
| C | existing Ensembl annotation | cohort | correct platform type |

If resources permit, repeat A with the main alternative for
`isoquant_report_novel_unspliced` and with `isoquant_check_canonical` enabled.

For annotation-free output, evaluate models using independent evidence:

- per-model and per-junction read support;
- support across independent accessions;
- transcript-end support;
- splice-site canonicality and plausibility;
- ORF/CDS and protein support;
- overlap with a trusted annotation only as an external comparator;
- reproducibility across accessions and backend methods.

Do not use the existing Ensembl annotation as ground truth for the primary
annotation-free benchmark. It can be used for a secondary known/novel
classification and for identifying obvious agreement or disagreement.

## 11. Validation requirements

### Static and stub validation

- Add schema coverage for every IsoQuant parameter.
- Validate that annotation-free mode rejects `isoquant_genedb`.
- Validate that reference-guided mode rejects a missing `isoquant_genedb`.
- Validate that unsupported `isoquant_data_type` values fail before execution.
- Run the all-backend native stub with IsoQuant enabled.
- Run IsoQuant-only annotation-free and reference-guided stubs.
- Confirm IsoQuant is invoked from the complete BAM channel, not contig-shard
  candidates.
- Confirm no IsoQuant output reaches TAMA/StringTie/tmerge merge processes.
- Confirm canonicalisation and final QC retain backend/scope metadata.

### Container validation

- Confirm the pinned container is available for Linux/amd64.
- Run `isoquant --version` and `isoquant --test` inside the container.
- Verify the container can read sorted/indexed BAM, FASTA, and GTF inputs.
- Record the IsoQuant and dependency versions in the pipeline versions file.

### Real-run acceptance criteria

A real run is acceptable only if:

1. every approved accession has an explicit IsoQuant status;
2. the cohort result records the complete BAM input list and checksum;
3. annotation-free output contains no annotation database input;
4. transcript models and read-evidence files are non-empty where mapped reads
   exist;
5. every published model set has a stable checksum and model count;
6. failed or empty scopes are not silently mixed into a successful cohort;
7. BED12 conversion passes structural validation; and
8. the output can be compared with the existing four backends without
   converting IsoQuant models through another backend.

## 12. Recommended implementation order

1. Pin and validate an IsoQuant container.
2. Add the schema/config parameters with annotation-free defaults.
3. Add a minimal IsoQuant-only process using one complete sorted BAM.
4. Add stable output discovery and manifest generation.
5. Add cohort execution over multiple complete BAMs.
6. Add annotation-free stubs and contract tests.
7. Add BED12 conversion and common finalisation/QC.
8. Add optional reference-guided mode.
9. Run the controlled benchmark matrix and publish a comparison report.

The first implementation should deliberately avoid adding IsoQuant to the
legacy common-merge path. The central invariant is that IsoQuant's native
transcript discovery and read-assignment evidence remain independently
inspectable.
